# Nyxia — Architecture Audit

Filesystem- and process-grounded audit. Verified against actual code, running processes, and installed
dependencies on this machine — not against `CLAUDE.md`, `README.md`, `PHASES.md`, or `.planning/STATE.md`
claims where those conflict with reality. Audit date: 2026-08-04.

**Process state at audit time:** the Electron app itself (`npm start` / `./launch.sh`) was **not running**.
Only `nyxia-vessel.service` (systemd --user, active) and a bare `ollama serve` process were live. `Status:
running` below therefore means "wired to the real entrypoint and actually called during normal app startup/
operation, per direct code inspection" — not "an active PID at this exact moment" unless stated otherwise
(vessel and Ollama are the only components independently confirmed as live processes right now).

**Note on doc staleness:** `docs/PHASES.md`, `.planning/STATE.md`, and `CLAUDE.md`'s own "Current State"
section are all frozen at March 2026 (mention an "RTX 4060 arriving soon" that was superseded by an RX 9070
XT 16GB, describe ElevenLabs as primary TTS when Qwen3-TTS is now primary, list Phase 10 agent loop as "Not
started" when `agent-loop.js` is fully built and wired). `docs/CHANGES.md` is current (entries through
2026-07-19) and `ARCHITECTURE.md` (also in this repo, undated) reads as recently and carefully verified —
most of its claims checked out against code in this audit, with two corrections noted below.

## 4. Duplication and conflict flags

1. **Tool definitions duplicated twice** — `src/nyxia-tools.js` (Anthropic tool-schema format) and `src/agent-loop.js`'s `TOOL_SCHEMAS` (Ollama/OpenAI format) define the same 7-8 tools (shell, web_search, fetch_page, fs_list/read/write, browser_action, desktop_action) independently. Updating one without the other silently desyncs what each brain can do. Confirmed by direct read of both files.
2. **Two training-data folders** — `training-data/` and `training_data/` (hyphen vs. underscore) exist side by side for the same fine-tuning-dataset purpose. Easy to update the wrong one; both are populated on disk.
3. **KRIX-BRAIN startup race** — `src/services/krix-brain.js` independently spawns `api.py`/`agent_api`/`server.py --http` if their health checks fail, while (per the task's ground truth) KRIX-BRAIN is also expected to run under its own systemd-managed lifecycle. At audit time the health checks succeeded and Nyxia's spawn logic was a no-op, but the *code path* for Nyxia to independently launch a second, Electron-child-process copy of KRIX-BRAIN's daemons exists and would fire if the systemd-managed instance were ever slow to respond — a real double-instance risk, not just theoretical.
4. **Brain-sector belief store is wired in but its backing service cannot start** — `brain-soul.js` calls a Chroma HTTP server on :8769 constantly (fireSector/getSelfBelief, used by `memory-manager.js` on every query). The Chroma binary `service-startup.js` looks for (`/var/data/python/bin/chroma`) does not exist on this machine, and the Python `chromadb` module isn't installed either — so every one of those calls fails silently (wrapped in `catch(_) {}` throughout). This is the clearest **"claimed working, actually broken"** finding in the audit: `ARCHITECTURE.md`'s own "Depends On" section lists ChromaDB as a working dependency, and `package.json` still lists the npm `chromadb` package (unused deliberately per that file's own comment) — but nothing currently keeps the belief-sector layer alive at runtime.
5. **Two conflicting model-string claims** — `CLAUDE.md` states the Claude model is `claude-sonnet-4-20250514`; `ARCHITECTURE.md` states `claude-sonnet-4-6`. Both are this repo's own docs, and they disagree with each other. Not independently resolved against `adapter.js`'s runtime default in this audit (out of time budget) — flagged as an internal doc inconsistency either way.
